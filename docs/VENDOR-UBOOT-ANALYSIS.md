## Findings so far

- At `0x00a02d10`, code requests global GPIO numbers `0x15`, `0x50`, and `0` with labels `power_usb_hub`, `power_usb_cam`, and `power_wifi_module` respectively. It calls the output-direction helper with value 1 and then the set-value helper with value 1. Return values are not checked by this caller.
- Direct static calls: `0x00a03e14 -> 0x00a03064 -> 0x00a02d10`. `0x00b045d8` is an entry in a contiguous function-pointer table; `0x00b272a8` is the addend of its relocation record, not a second independent callback. The dispatcher at `0x00a19fd8` invokes `0x00a9cc90` with the table at `0x00b044c0`, and that function iterates until a null entry or a callback returns an error. There is no null entry before `0x00b045d8`. Thus this code is on the normal initialization path if all preceding callbacks succeed. The published Rockchip `common/board_r.c` has the corresponding `initcall_run_list(init_sequence_r)` and `board_late_init` pattern, and `arch/arm/mach-rockchip/board.c` has the corresponding MAC setup and download-mode ordering. This is static analysis, not a runtime trace.
- The GPIO-number resolver at `0x00a68844` searches registered GPIO controllers and their dynamically assigned ranges; GPIO number 0 must not be assumed to mean Linux GPIO0_C0 without confirming controller registration order and ranges.
- The embedded U-Boot DTB declares GPIO0, GPIO1 and GPIO2 aliases for controllers at `fdd60000`, `fe740000` and `fe750000`; each node declares a 32-pin range. The published Rockchip GPIO uclass assigns global bases by iterating active devices in uclass order. Consequently the first active controller gets global GPIO 0 regardless of its alias, and later probes can renumber devices. If GPIO0 is first active, global 0 means GPIO0_A0, not GPIO0_C0. The actual registration/probe order remains unverified.
- Read-only inspection of the currently running Linux system reports its Wi-Fi pwrseq reset as GPIO0_C0 (offset 16), with GPIO0_A0 neither mux-claimed nor GPIO-claimed in that snapshot. `pinconf-pins` reports GPIO0_A0 as output low and GPIO0_C0 as output low; the latter is active-low reset. The snapshot is after unsuccessful enumeration, not evidence of either line's level during original U-Boot or initial enumeration.
- The configured Linux 7.2 source `drivers/mmc/core/pwrseq_simple.c` sets logical reset 1 in `pre_power_on`, logical 0 in `post_power_on`, and logical 1 in `power_off`. For an active-low line those correspond to physical low, high, and low, respectively. Therefore the post-failure low snapshot is compatible with ordinary cleanup and does not demonstrate that reset remained asserted during CMD5. These are source-level expectations, not a sampled waveform or proof of the running module's exact build provenance.
- The embedded U-Boot FDT marks GPIO2 `u-boot,dm-pre-reloc`, while GPIO0 and GPIO1 are marked `u-boot,dm-spl`. Public Rockchip `common/board_r.c` reconstructs the driver model after relocation with `dm_init_and_scan(false)` before `board_late_init`. Consequently early probe history alone cannot establish the later GPIO uclass ordering. Matching the public source to this particular binary and the actual post-relocation device ordering remain necessary before assigning global GPIO 0 to a physical pin.
- The original binary contains a further material complication: init-table entry `0x00a04228` occurs before `0x00a03e14` and calls `0x00a04e30`. The latter prints `DM: v1`, uses `fdt_addr_r` (or `fdt_addr1_r` for small RAM), calls a DTB loading routine and, on successful load or available embedded fallback, sets the working FDT pointer, performs phandle adjustments, rebuilds the live tree and scans devices. Its strings and control flow match the public Rockchip `arch/arm/mach-rockchip/kernel_dtb.c` function `init_kernel_dtb()` with `CONFIG_USING_KERNEL_DTB_V2` disabled. The caller ignores its return value. Hence the FIT's RK3568 EVB FDT is not necessarily the working FDT when `power_wifi_module` is requested: it depends on whether a kernel DTB could be loaded in that particular boot. This also means an apparent U-Boot difference may depend on an earlier Linux DTB, but the actual loaded DTB and success path have not been observed. Source reference: https://github.com/rockchip-linux/u-boot/blob/next-dev/arch/arm/mach-rockchip/kernel_dtb.c
- Early DTB loading is separate from the later extlinux `FDT` directive. `0x00a03704` calls `0x00a071a4`, which searches a Rockchip resource-file list and falls back to `rk-kernel.dtb`, reads the selected file, and validates its FDT header. `0x00a06c40` first examines the boot/recovery image and falls back to a partition named `resource`; it accepts a resource image or standalone DTB and reports `Found DTB in %s part`. The binary's list walk records a non-default DTB when present and otherwise uses `rk-kernel.dtb`; exact multi-DTB selection requires further verification. On successful load `0x00a03704` also checks an available 20- or 32-byte hash. Runtime boot media, partition layout, resource contents, fallback and live logs decide which DTB was selected. Neither this early resource selection nor its success can be inferred from extlinux configuration alone. Related published source: https://github.com/rockchip-linux/u-boot/blob/next-dev/arch/arm/mach-rockchip/resource_img.c
- The binary's GPIO request helper `0x00a68ab4` rejects an already-labelled line and otherwise optionally invokes a driver `request` callback before recording the label. `0x00a68cc4` and `0x00a68d70` check only that a label exists, not that it belongs to this caller. As `0x00a02d10` ignores the return values, a failed request does not stop this initialization chain, and an already-claimed line may still pass the subsequent reservation check. Pinmux configuration, ownership and actual hardware writes still require verification; the label by itself does not prove a physical output changed.
- The `gpio_rockchip` driver registration at `0x00b134c8` points to the operations table at `0x00acb8d0`. In this table the `request` callback is null, while direction-output and set-value point to `0x00a6918c` and `0x00a690b8`. The former writes data then direction registers, and the latter writes data registers; neither calls a pinctrl/mux-setting function. This agrees with the published Rockchip driver. Therefore, conditional on this driver handling the global number and the operation passing reservation checks, these calls manipulate GPIO registers but cannot themselves ensure the pin is muxed to GPIO. It remains unverified which bank is selected, whether pinmux was set earlier, or whether these writes reached the hardware.
- `vcc9-supply` appears in `0x00a83b78` alongside `vcc8-supply`, conditionally for PMIC identifiers `0x8090`/`0x8170`; the string alone does not establish a Wi-Fi power action.
- Static evidence does not establish the pin's physical level at Linux handoff or prove that this difference caused the observed SDIO failure.

## Default boot environment

`uboot-default-env.txt` is the NUL-separated built-in environment rendered as lines, starting at U-Boot file offset `0xc0ed0` for `0xebc` bytes. At `0x00a93ec8`, the binary imports that range when selecting the default environment. This is not proof of the live environment: persistent environment and board-time changes may override it.

- The captured built-in default is `bootcmd=sysboot mmc 0:9 any 0x00c00000 /extlinux/extlinux.conf` and `bootdelay=0`.
- A separate `distro_bootcmd` and `boot_targets=mmc1 mmc0 mtd2 mtd1 mtd0 usb0 pxe dhcp` are compiled in, with USB scanning functions, but the captured default `bootcmd` does not call `distro_bootcmd`. Their presence does not imply USB-first boot.
- Code at `0x00a1717c` reads `preboot` and executes it when present, then proceeds to boot-command processing. Code at `0x00a03064` can modify `preboot` for recovery, USB download, charge and UMS boot modes before the main loop. Empty built-in `preboot` alone does not prove it stays empty at runtime.
- Built-in console values include `stdin=serial,usbkbd` and `stdout=serial,vidconsole`; these strings do not prove that a given keyboard or display is initialized and usable.

## Runtime confirmation of the Wi-Fi power line

On 2026-10-28 the running Z96A Armbian 7.2.11 system (root on USB `/dev/sda2`) was used for a reversible runtime test. Linux exposes GPIO0 with a global sysfs base of 512, so GPIO0_A0 is global GPIO 512. At baseline, pin 0 was output-low and unclaimed. Unbinding and rebinding only `fe2c0000.mmc` reproduced the known `CMD5` timeout and no SDIO card.

Asserting GPIO0_A0 high before the same `mmc1` rebind changed the result immediately: `mmc1:0001` enumerated, `rtw88_8822cs` loaded firmware 9.9.15, and `wlan0` appeared. The card still reported a non-fatal `CMD11` timeout and fell back from SDR104 to 50 MHz high-speed, after which Wi-Fi scanned and connected successfully. Releasing A0 low while the interface remained registered caused continuous `rtw88` SDIO read/write errors (`-110`/`-16`). This confirms A0 as the persistent module power/enable line rather than a one-shot reset.

The vendor U-Boot's three numeric GPIOs also cross-check consistently with the controller layout: `0x50` (80) is GPIO2_C0, the known camera power enable, and `0` is GPIO0_A0. This makes the static U-Boot mapping conclusion much stronger, while the runtime A0 test independently establishes the Wi-Fi behavior.

The first persistent test used a GPIO0_A0 output-high hog. It made SDIO enumerate on every boot, but `rtw88` failed its first probe and recovered only after an explicit `mmc1` rebind. A second DTB modeled A0 as a `regulator-fixed` behind `sdmmc1`'s `vmmc-supply`; this established a valid power rail and kept the existing 50 MHz non-SDR104 configuration, but the first `rtw88` probe still failed when Bluetooth firmware initialized concurrently.

The final successful configuration is [current-wifi-regulator.dtb](current-wifi-regulator.dtb), with the matching build patch [0002-z96a-wifi-power-rail.patch](0002-z96a-wifi-power-rail.patch). It uses the A0-controlled `vcc_wifi` regulator, `vcc3v3_sd` always-on/boot-on, and 50 MHz non-UHS SDIO. `hci_uart` is blacklisted from automatic startup; a systemd oneshot waits until `rtw88_8822cs` is loaded and `wlan0` is connected, then loads Bluetooth. A clean reboot produced SDIO enumeration at 2.16 s, stable Wi-Fi firmware at 7.36 s, `hci0` at about 26 s, Wi-Fi on `192.168.31.85`, and an HTTP 204 connectivity check. Wi-Fi remained connected while Bluetooth initialized.

## Z96A charger path in U-Boot

The `z96a-pwr` path in the U-Boot 2026.01 image was decompiled from U-Boot image 0. The normal `initcall_run_r` path reaches `FUN_008036c4` (board late init), which calls `FUN_00804284` at address `0x00804284`. The readable reconstruction is [z96a-pwr-reconstructed.c](z96a-pwr-reconstructed.c); complete excerpts are in [charger-functions.c](charger-functions.c) and [charger-selected-functions.c](charger-selected-functions.c).

U-Boot reads SC8886 status/ADC bytes, always writes PROCHOT defaults `0x36=0x65` and `0x37=0x4a`, and selects the power source. When AC_STAT is set it clears the OTG bit in `0x32`, updates `0x12`/`0x14`, and logs a 1024 mA charge-current setting; with AC absent it leaves the source on battery or reports no usable power. It does **not** write the QC protocol-chip reset, does not write `RESET_VINDPM` in `0x35`, and exposes no additional QC reset GPIO. Therefore U-Boot does not contain a software-only fix for a fully locked QC chip. Its only useful missing parity in Linux is the explicit PROCHOT-default restore and power-path/current setup.

The older factory-style 2017.09 U-Boot decompilation also contains a charger path at `0x00a7dcc0`/`0x00a7e3bc`. For the SC8886/BQ25703 family it reads charger register `0x00`, clears the watchdog field, writes `0x0c=0x1200`, chooses `0x0e=0x1e00` or `0x0a00` from the USB type, and if AC_STAT is present writes `0x02=0x0400` (1024 mA). Neither factory-style path writes the QC-chip reset or `RESET_VINDPM`.

On a currently charging system the relevant SC8886 values were `0x20=0x00`, `0x21=0x84` (AC_STAT via the 16-bit `0x20` view), `0x27=0xb5` (VBUS about 14.72 V), `0x32=0x37`, `0x36=0x65`, and `0x37=0x4a`, already matching U-Boot defaults. A 60-attempt, one-second `RESET_VINDPM` test recovered `online=1` at attempt 25, but the state fell back to `online=0` about five seconds after the loop stopped. This proves that repeated reset alone is only a transient rescue; any recovery implementation must include a bounded post-recovery stabilization interval and charger reconfiguration rather than stopping on the first AC_STAT transition.

Candidate kernel patch [0014-bq257xx-bounded-recovery.patch](0014-bq257xx-bounded-recovery.patch) implements that sequence: it starts a 60-second recovery window on charger-offline transitions, issues at most one `RESET_VINDPM` per second while offline, restores the U-Boot-equivalent SC8886 PROCHOT/OTG/charge settings when AC first returns, and stops only after ten consecutive online seconds or timeout. The patch applies cleanly to the current 0012 worktree and `bq257xx_charger.ko` compiled for `7.2.12`. The candidate module was loaded on the device without regression: `online=1`, `status=Charging`, current about 960 mA, capacity 61%. A physical unplug/replug test is still required to validate the recovery window.

The Android backup `z96a_full_no_userdata_20260818.img` was parsed into its GPT partitions. `boot` and `recovery` both contain the same Android kernel image and Rockchip RSCE `rk-kernel.dtb`. The DTB confirms the vendor SC8886 nodes, `charger_ok` on GPIO0_C2, and the Type-C mux on GPIO4_D2 (`switch-ctl-gpios`, represented in Linux as the existing `usb-switch` orientation mux). It contains no QC-chip reset or enable line. The Android vendor `bq25700_charger` source uses the BQ25700 register map (`0x14` charge current, `0x3d` input voltage, `0x3f` input current), while the working Linux SC8886S path uses the BQ25703 map (`0x02`, `0x0a`, `0x0e`); probing both sets showed the latter has meaningful values while `0x12..0x15` read `0xff`. The vendor driver has no `RESET_VINDPM` recovery path.

Recovery experiments on the live system established a reliable physical/electrical recovery sequence: turn the smart plug off, wait 5 seconds, power off the Z96A, wait about 25 seconds, turn the plug on, and wait for auto-boot. A single plug off/on while the SoC remains running did not recover. Runtime `rt1711h` unbind/rebind produced a `tcpm_port_unregister_pd` devres warning and did not recover. Writing HUSB311 soft-reset (`0xA0=0x01`) also made AC fall offline. The validated recovery is therefore a full power removal plus SoC power cycle, not a runtime Type-C controller reset. A Home Assistant API control helper is available at [ha_switch.py](ha_switch.py); credentials remain environment-overridable and are not written by the script.

The vendor BQ25700 register map puts `RESET_VINDPM` at `0x32` bit 13, unlike the BQ25703-style `0x35` bit 5 used by the current patch. A live test read `0x32` as `0x02b7`, set bit 13 (`0x22b7`), and observed AC change from `online=1 / Not charging / 0x8c00` to `online=0 / Discharging / 0x0000`. Thus both reset encodings disrupt the current negotiation but neither recovers a locked QC path. Runtime charger/Type-C resets are ruled out by evidence; only full adapter and SoC power removal reliably restores charging.

A final Type-C experiment cut the smart plug first, waited five seconds, then reset HUSB311 while VBUS was absent and powered the plug back on. The charger still ended at `online=0 / Discharging`, while the red LED briefly remained on, reproducing a short AC-status flash without stable charging. This confirms the observed red blink can be a transient state/race rather than a 9-second/1-second charge cycle requiring software polling.

A longer version of the same test held VBUS off for 25 seconds after HUSB311 soft reset before restoring the smart plug. It also ended at `online=0 / Discharging`; giving the CC/QC path more time to discharge did not make a runtime controller reset sufficient. The only validated recovery remains simultaneous adapter and SoC power removal. The exact sequence is automated in [recover_z96a_power.sh](recover_z96a_power.sh), which completed multiple live cycles and restored `online=1 / Charging / ~960 mA`.

The BQ25703 VINDPM register was also tested explicitly. While charging, writing `0x0a=0x1dc0` (about 15 V VINDPM) kept `online=1 / Charging / 960 mA`. A subsequent smart-plug off/on then dropped VBUS to zero and left `online=0`; the chip had reloaded `0x0a=0x0200`. Therefore a high VINDPM setting alone does not preserve or restore renegotiation across adapter removal.

The `.132` charger watchdog now runs from cron every five minutes. It tolerates up to 60 seconds of temporary offline state with two rechecks before invoking the full power-cycle recovery. An end-to-end fault injection first observed `online=0 / Discharging`, then recovered to `online=1 / Charging / 960 mA` before any restart was needed; the watchdog logged `OK_AFTER_RECHECK`. This shows a substantial subset of failures is transient and should not trigger an immediate SoC power cycle.

After the final recovery, a 120-second no-intervention sample showed `online=1` and `status=Charging` for the entire interval, with the red LED continuously on. Only the charger's reported current changed between 896 and 960 mA; there was no alternating offline/online cycle. The user-observed brief red flash is therefore not reproduced as a sustained 9-second discharge/1-second charge duty cycle in the stable state.

## Mainline comparison

The build cache at `/home/hsy/project/armbian-z96a-2026.01-extlinux/cache/sources/u-boot-worktree/u-boot-rockchip64/rockchip-v2026.01` contains Z96A-specific `board.c`, `rk3568-z96a-laptop-v2.dts` and U-Boot DTS include. The board code's `rk_board_late_init()` handles charger/power-source setup but contains no `power_wifi_module` GPIO sequence; the built `u-boot` does not contain that vendor label. Its `.config` enables `CONFIG_DM_GPIO` and `CONFIG_BOARD_LATE_INIT`, but has `CONFIG_GPIO_HOG` disabled.

On 2026-10-28 the first 4 MiB of `.84` eMMC sector 16384 were read without writing the device. The first 1,220,096 bytes compare byte-for-byte equal to this cache's `u-boot.itb` (SHA-256 `efd764f4aaf53ec588884447b38c1a5b4b3d301cbf3081398330f9272e7a2895`), and the extracted region identifies itself as `U-Boot 2026.01-armbian`. The 4 MiB region SHA-256 is `87e522e3b5838e7df24dd7d5622d4c5bd4d4c0f067d412043d3ca94ec824949c`. This proves the comparison applies to the FIT presently stored at that location; the read alone does not attest the actual boot source or runtime execution history.

The later runtime test closed the earlier physical-mapping gap: GPIO0_A0 is the persistent Wi-Fi module enable/power line, and asserting it makes SDIO enumerate and `wlan0` appear. This makes the missing vendor U-Boot initialization a confirmed behavioral difference; it does not require replacing U-Boot because the same line can be owned safely by the Linux board DTB.
