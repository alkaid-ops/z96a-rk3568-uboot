# Z96A eDP RAM-test notes, 2026-11-11

These are experimental RAM-chainload tests, not production U-Boot builds.
No eMMC bootloader or partition table was written.

The manually bound VOP device was created with `device_bind()`, which passes
zero as driver data. The VOP driver subsequently uses that value as its
SoC-specific callback and platform-data pointer. The test now uses
`device_bind_with_driver_data()` with `rk3568_driverdata` and verifies the
pointer before probing. This is a confirmed code defect; its relationship to
each earlier failure is not independently proven.

The FAT stage-marker length was also corrected from decimal formatting to the
hexadecimal expected by `fatwrite`. The temporary extra CRU read-modify-write
was removed: Rockchip clock gates use high-half write masks. In the observed
test the gate read back as zero, but the old write cannot establish that it
opened the gate.

Root-cause candidate from the vendor-binary comparison, supported by code inspection of the local tree: the eDP video timing configuration registers (0x48-0x88: total_line, active_line, v_f_porch, vsync width, v_b_porch, total_pixel, active_pixel, h_f_porch, h_sync, h_b_porch) are never written anywhere in `drivers/video/rockchip/rk_edp.c` or the rest of the test tree. The vendor driver programs them in `analogix_dp_set_video_format` (vendor analogix_dp_reg.c:1079-1136) before `config_video`, and its `config_video` always selects register timing (`VIDEO_CTL_10.F_SEL` cleared, vendor analogix_dp.c:839). With `F_SEL` cleared and all timing registers at reset values the controller has a zero active region, which would produce a link that trains and reports `STRM_VALID` while showing no pixels — consistent with all observations so far. The register map itself was cross-checked: the local `struct rk3288_edp` offsets agree with the vendor header at every field used (video_ctl_4 at 0x2c, video_ctl_10 at 0x44, sys_ctl_4 at 0x60c, buf_data_ctl at 0x790, soc_general_ctl at 0x800), so this is not a layout mismatch. Additional vendor-parity gaps closed in this build: VIDEO_CTL_10 sync-polarity bits (bit 1 set for the panel's low-active vsync, bit 0 clear for high-active hsync; the RK3288-era code never set them), SOC_GENERAL_CTL (`AUDIO_MODE_SPDIF_MODE | VIDEO_MODE_SLAVE_MODE`, previously untouched/reset), and FUNC_EN_1 master/slave video bits (`MASTER_VID_FUNC_EN_N` set, `SLAVE_VID_FUNC_EN_N` clear; the old code cleared unrelated bits instead). These are vendor-derived but not yet independently proven necessary.

The stream-valid regression identified the missing piece: the vendor RK3568 controller init (`FUN_00a656ec` at `artifacts/vendor-uboot/uboot-decompiled.c:75247`) writes FUNC_EN_1 (0x18) = `0xbd`, a mask that disables master video, slave video, audio FIFO, audio, HDCP and SW blocks but explicitly leaves `VID_CAP_FUNC_EN_N` (bit 6) clear. The RK3568 reset value of that bit is 1, so builds that never write this mask leave video capture disabled. This explains both earlier symptoms at once: the older build cleared bit 6 by clearing `VID_FIFO_FUNC_EN_N | VID_CAP_FUNC_EN_N`, which made `STRM_VALID` assert even though the timing registers were still zero and no pixels existed; the timing-fix build kept bit 6 at its reset value, so the stream check now correctly failed. Writing the vendor value enables capture, while programming the timing registers supplies a non-zero active region.

Manual FIT rebuild failure, four times, and the missing-`entry`/missing-`os` root cause. After `logo-mmc-v1` was proven through the RAM chainload, the same `u-boot-nodtb.bin` (1,015,688 bytes) plus `u-boot.dtb` were repacked with a hand-written ITS into a FIT placed at sector `0x4000`. Four consecutive flashes produced a completely dead board (no display, no NIC LED, no serial), each time recovered through maskrom. Size was ruled out: the 1,288,048-byte FIT is only 5.5% larger than P1 and fits the SPL load window (`0x00800000..0xA58F78`) with the stack (`0x03e00000`) and BSS (`0x03f80000`) clear. The RAM chainload had always used `go 0x10000000` on a pre-joined nodtb+dtb binary, so it never exercised SPL FIT parsing at all.

Source inspection of `common/spl/spl_fit.c` explains the failure exactly. `spl_fit_...` resolves the image entry as follows:

- `fit_image_get_entry()` on the firmware/config node falls back to the load address of the **first loadable** when no explicit entry is present; the comment at `spl_fit.c:919-921` and the lookup at `:360-368` show this. With `atf-1` lacking `entry = <0x00040000>`, the SPL jumped to `0x00800000`, i.e. straight into U-Boot, skipping TF-A entirely, so ATF never initialized the secure world/DRAM handover and the board died (fatal exception, no console since ATF owns early UART setup).
- The devicetree is only appended to a loadable whose `os` says it takes one: `os_takes_devetree()` (`spl_fit.c:939-940`) returns true for `os = "u-boot"`. The hand-written `u-boot` node omitted `os`, so `fdt-1` was never attached and U-Boot ran without its control DTB.

P1 was generated by binman, which writes both properties automatically, which is why P1 alone ever booted. The corrected hand-written ITS template (now `build/out/fitfix-v2/z96a-uboot.its`) carries `atf-1 entry = <0x00040000>` and `u-boot os = "u-boot"` explicitly; every future manual repack must reuse it and must be checked with `dtc` after packing.

`fitfix-v1` was flashed at sector `0x4000` with the unchanged idbloader `35c368f3...`. It boots: power LED at ~2 s, logo at ~8 s, USB Devuan normal, eMMC fallback intact. Verification after packing: `dtc` decompile shows `atf-1 (load=0x40000, entry=0x40000)` and `u-boot (os="u-boot", load=0x800000, entry=0x800000)`.
