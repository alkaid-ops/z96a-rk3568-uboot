# Z96A U-Boot bring-up runbook (Phase 0 / Phase 1)

All steps below are done from the Z96A serial console or the `.132` host.
Nothing here writes eMMC.  eMMC write is a separate, explicitly authorised
step at the end.

## 0. What was built

`build/build-uboot.sh` rebuilds U-Boot proper + the control DTB and repacks
them with the TF-A blobs extracted from the currently deployed FIT
(`build/atf/atf-1..6.bin`, hashes match the deployed FIT).  No rkbin/BL31
download is needed and idbloader/SPL are not rebuilt.

Baseline output (`TAG=baseline-20261110`):

```text
build/out/baseline-20261110/u-boot.bin            full FIT (eMMC payload)
build/out/baseline-20261110/u-boot-fit-dtb.bin    nodtb + dtb (RAM test)
build/out/baseline-20261110/z96a_chainload.bin    RAM chain-load stub
build/out/baseline-20261110/SHA256SUMS
```

Second build (`TAG=led-first-20261110`) adds:

- `gpio-leds` nodes for the three front LEDs in the U-Boot DTB;
- `z96a_leds_immediate()` / `z96a_leds_update()` in `board.c`
  (power LED on as soon as `board_late_init()` runs, charger state
  mapping from SC8886 `0x20`/`0x21`);
- `z96a_charge_gate()` and `z96a_charge_loop()`;
- a manual test command `z96a-charge`.

Third build (`TAG=led-charge-v2-20261110`) is the current candidate.  It
adds one rescue rule: before sitting in charging mode, it probes USB
once and boots immediately if a storage stick is present.  The PMU_GRF
marker idea was dropped after the Phase 1 test showed warm reset clears
those registers (see below).

## 1a. Verified power-on semantics (hardware, 2026-11-10)

RK809 `ON_SOURCE` (`0xf5`) measured on the real board:

| scenario | value | meaning |
|---|---|---|
| cold charger plug-in (device off) | `0x40` | `PLUG_IN`, no `PWRON` |
| power button / HA “电脑” relay | `0x80` | `PWRON`, no `PLUG_IN` |
| Linux `reboot` (AC connected) | `0x02` | neither bit |

PMU_GRF `0x21c` (OS_REG7) was written to `0x5A96C001` and read back as
`0x0` after `reboot`, so OS registers do not survive a warm reset.
The gate therefore needs **no reboot marker**: `reboot` reports
`0x02`, which never matches `PLUG_IN`.  Three repeated reboots all
reported `0x02`.

`INT_MSK0` (`0xf9`) is `0xdc`, so the PWRON fall/rise interrupts are
already unmasked.  `INT_STS0` reads `0x00` under Linux because the
kernel `rk805-pwrkey` driver consumes and clears the status; polling it
from U-Boot (no kernel driver) still has to be confirmed on hardware
with `z96a_charge`.


Source changes vs the pinned `8e474aa` tree are exported in
`build/patches/0001..0004`.  The DTB generated by the baseline build is
byte-identical to the DTB inside the deployed FIT (`3f19b134...`), and
the FIT image layout/load addresses match the deployed one exactly.

## 1. RAM chain-load test (eMMC untouched)

Copy these files to the FAT boot partition of the USB stick
(the partition Linux mounts as `/boot`, normally `p1`).  On the current
test unit they are already staged under `/boot/z96a-uboot/`:

```text
u-boot-fit-dtb-baseline.bin
u-boot-fit-dtb-ledcharge-v2.bin
z96a_chainload.bin
SHA256SUMS
```

Reboot the machine, interrupt with Ctrl+C at the U-Boot prompt, then
(use the baseline first):

```text
usb start
ls usb 0:1 /
load usb 0:1 0x00800000 u-boot-fit-dtb-baseline.bin
load usb 0:1 0x10000000 z96a_chainload.bin
go 0x10000000
```

What should happen:

1. New U-Boot prints its banner (version `2026.01-armbian ...`).
2. It re-runs its own USB scan and boots the USB stick via extlinux.
3. If it boots to Linux, Phase 0 is validated.

If anything hangs or the screen/console dies:

- power-cycle the board;
- the eMMC U-Boot comes up unchanged, because nothing was written;
- record what the last console line was.

Run this at least 3 times (including one after a full power removal)
before trusting the recipe.

### Optional: verify the loaded image before jumping

```text
load usb 0:1 0x00800000 u-boot-fit-dtb-baseline.bin
crc32 0x00800000 <size>          # compare with SHA256SUMS note
md 0x00800000 4                  # should start with U-Boot ARM64 code
```

## 1b. Manual charging-mode test from RAM (new U-Boot only)

With the candidate build loaded via `go`, at the new U-Boot prompt:

```text
z96a_charge
```

Expected:

- console prints `z96a-charge: charging mode; ...`
- the white power LED is on; red/green follow the charger state;
- pressing the power key (short press) prints
  `z96a-charge: power key pressed, booting` and returns to the prompt;
- Ctrl+C also returns to the prompt;
- no automatic boot happens while the command runs.

This validates LED mapping and power-key polling without any eMMC write.
After it returns, `boot` continues the normal USB-first boot.

If the power-key text never appears on a short press but Ctrl+C works,
the RK809 `INT_STS0` polling assumption is wrong; do not enable the
automatic cold-plug gate until that is fixed (Phase 1 data will tell us
whether the PMIC latches PWRON edges without IRQ setup).

## 1c. Automatic charge-mode gate test (later, after Phase 1)

The automatic gate is compiled in, but it only triggers on a cold
plug-in event (`ON_SOURCE` PLUG_IN without PWRON).
To test it safely from RAM:

1. load and `go` the new U-Boot as above;
2. at the prompt run `z96a_charge` once to confirm the loop;
3. return to the prompt, then run `reset`?  No: `reset` restarts the
   board and the eMMC U-Boot runs instead.

Because the new U-Boot only lives in RAM, the automatic gate cannot be
exercised by a real power cycle until the FIT is written to eMMC.  The
RAM tests therefore validate the mechanism (`z96a_charge`) and Phase 1
validates the PMIC semantics; the first real cold-plug test happens
right after the (separately authorised) eMMC write.

USB rescue rule: before entering charging mode, the gate probes USB
once.  If a USB storage stick is present, it prints
`z96a-charge: USB stick present, normal boot` and boots normally, so a
rescue stick inserted before the charger is never blocked by charge
mode.

## 2. Phase 1 read-only meaning probe (Linux running, no reboot)

From the running USB-booted Linux, as root:

```sh
cd /path/to/rea-z97a/build/phase1
./phase1-z96a-probe.sh > /tmp/phase1-$(date +%F-%H%M).log
```

Send back the log.  It reads:

- RK809 `ON_SOURCE`/`OFF_SOURCE` (`0xf5`/`0xf6`): was this a PWRON or
  a plug-in power-up?  (already measured: `0x40` plug-in, `0x80`
  power key, `0x02` warm reboot)
- `PMU_GRF 0x200..` OS registers: do they survive a warm reset?
  (already measured: no, so no reboot marker is used)
- RK809 `INT_STS0`/`INT_MSK0` (`0xf8`/`0xf9`): is the power key
  observable by polling from U-Boot?  (mask is open; Linux consumes and
  clears the status, so U-Boot still needs the `z96a_charge` test)
- LED GPIO0_D3/D5/D6: ownership, direction, polarity, and which physical
  LED lights up.
- SC8886 `0x20/0x21/0x26/0x32/0x36/0x37`: AC / fast-charge / pre-charge
  bits in the current state.
- Boot timing from `dmesg`/`systemd-analyze`: how much of the ~10 s is
  U-Boot, kernel, DRM, and the charger/LED drivers.

The script only reads and briefly toggles the LED GPIOs, restoring them
afterwards.  It does not reboot, does not touch eMMC, and does not write
charger configuration.

### Additional scenarios needed (one per power cycle)

For each scenario, note the `ON_SOURCE` and OS-register values:

1. Full power off (battery + adapter removed), then plug the adapter in.
2. Full power off, then press the power button (no adapter).
3. Full power off, then press the power button while the adapter is
   plugged in.
4. From Linux with the adapter plugged in: `reboot`, then immediately
   re-read the same registers.

This is the evidence that decides whether Phase 3 can reliably
distinguish "cold plug-in" from "user pressed the power button" and
whether the `reboot` guard works.

## 3. After Phase 1: LED patch (Phase 2)

Once the LED GPIO facts are confirmed, `board.c` gets an early LED init
so the power LED lights within ~1 s of the button press.  It is compiled
and RAM-tested with the same stub above before any eMMC write.

## 4. eMMC write (gated, not yet)

Only after:

- the baseline RAM chain-load works at least 3 times;
- the LED build works from RAM;
- the charge-mode build works from RAM;
- explicit user authorisation for the write;

then, from the running USB Linux:

```sh
# sanity: what is currently on eMMC uboot region (8 MiB..12 MiB)
sudo dd if=/dev/mmcblk0 bs=1M skip=8 count=4 | sha256sum
# expected 87e522e3b5838e7df24dd7d5622d4c5bd4d4c0f067d412043d3ca94ec824949c

# write the new FIT (1.2 MB, offset 8 MiB)
sudo dd if=u-boot.bin of=/dev/mmcblk0 bs=1M seek=8 conv=fsync
# read back and compare
sudo dd if=/dev/mmcblk0 bs=1 count=$(stat -c%s u-boot.bin) skip=$((8*1024*1024)) | sha256sum
```

Rollback is the same command with the previously saved `u-boot.bin`
(copy from `artifacts/mainline-uboot/u-boot.bin`, sha256
`efd764f4...`, and also keep a copy on the USB stick).

Do not touch GPT, `misc`, `idbloader` or the `boot` partition.
